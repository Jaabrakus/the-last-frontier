## Why the API is channel-local

`WorldRiver` is one-dimensional in z: 40 files call it, 99 times `x_at(z)`, plus `level_at`, `flow_at`, `rapid_at`,
`z_range`. A network with a west-east torrent has no single x for a given z, so a drop-in replacement is impossible.
Phase 3 M0 keeps WorldRiver for R1's z-monotonic main channel; M1 ports the callers to this class one by one. Your job is
the class those ports will target, plus a bridge M0 can use.

## Build

- `tools/environment/water/build_water_json.py`: generates `data/world/maps/r1/water.json` from `layout.json`
  (channels with bed profiles, junctions, pounds as polygons, reaches, the lock step marked for M2). Nobody hand-edits
  `water.json`.
- `scripts/world/water/water_network.gd` (class `WaterNetwork`, RefCounted, loaded from `water.json`):
  - `channel_at(pos: Vector3) -> Dictionary` with `channel`, `s` (metres along), `offset` (signed, from the centre
    line), `half_width`, or empty
  - `surface_at(x, z) -> float` (`NO_WATER` outside), `depth_at(x, z, ground: Callable) -> float`,
    `current_at(x, z) -> Vector3`, `is_under_water(p: Vector3) -> bool`
  - `set_reach_flow(reach_id, scale)`; flow is `scale` inside the reach and eased over `ease_m` at its ends; a reach's
    scale by world state comes from `scale_by_state`
  - `pound_level_at(pound_id, day: float) -> float`: the downstream drop as a world-state curve
  - `as_world_river_block(channel_id) -> Dictionary`: for z-monotonic channels only, the piecewise x(z) and level(z)
    nodes plus reaches, in the form Phase 3 M0's WorldRiver extension will read; returns empty for the torrent
- `tools/environment/water/water_net.py`: the same maths in numpy, for T4's carving and for plots.
- `tools/environment/water/plot_network.py`: the internal plots.
